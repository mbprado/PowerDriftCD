# 2026-10-16 BIOS-backed emulator check

**Question/hypothesis:** will the original-code Phase 0 disc pass a European Mega CD BIOS and execute its sub-68000 marker in two independent emulators? **Expected evidence:** sub-CPU breakpoint/step at the initial program (IP), followed by `D0 = 0x50443030`; a second emulator reaches the same program. **Result:** firmware boot `PASS` in BlastEm and Genesis Plus GX; disc IP execution `FAIL` in the observed runs; both-CPU debugger access in BlastEm `PASS`; exact rejection cause `INCONCLUSIVE`; physical hardware `NOT RUN`. This is an L1 emulator test with an independent L2 cross-check of the BIOS screen, not an L2 game-boot pass.

## Interpretation and next action

**Verified by execution:** both emulators loaded the owner-supplied EU BIOS and displayed its UI while given the same ISO/CUE image. BlastEm progressed to the CD player after Start, and the sub-CPU marker `D0 = 0x50443030` was not observed. This fails the intended disc program boot test. The Genesis Plus GX still frame alone cannot rule out a later response to Start, and that core run did not expose CPU state. **Documented only:** [Mega CD development notes](https://rhope.retrodev.com/segacd.html) and the [disc-format specification/security bulletin](https://gist.github.com/akiyan/a90d1e7d41ce89c532f29cafc356ccc2) describe BIOS security/startup requirements. **Hypothesis:** the generated image lacks a region-specific security/startup sequence accepted by the BIOS; header details or image format may also contribute. **Unsupported:** a definitive rejection reason, successful original-code BIOS handoff, hardware compatibility, Word RAM/ASIC timings, or hardware-equivalent frame pacing.

**Next action:** research and implement only an independently authored lawful startup path if feasible, then require the marker breakpoint and independent emulator pass before Phase 0 review. A dedicated Word RAM/ASIC/VDP synthetic test follows after boot. The renderer gate remains closed.
