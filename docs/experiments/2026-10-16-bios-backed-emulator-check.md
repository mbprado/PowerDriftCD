# 2026-10-16 BIOS-backed emulator check

**Question/hypothesis:** will the original-code Phase 0 disc pass a European Mega CD BIOS and execute its main-68000 marker in two independent emulators? **Expected evidence:** main-CPU breakpoint/step at the initial program (IP), followed by `D0 = 0x50443030`; a second emulator reaches the same program. **Result:** firmware boot `PASS` in BlastEm and Genesis Plus GX; disc launch `FAIL` in the observed runs; both-CPU debugger access in BlastEm `PASS`; exact BIOS rejection path `INCONCLUSIVE`; physical hardware `NOT RUN`. This is an L1 emulator test with an independent L2 cross-check of the BIOS screen, not an L2 game-boot pass. **Correction (2026-10-16):** the first version of this record incorrectly treated IP as sub-CPU code. The IP executes on the main 68000; SP is sub-CPU code. Therefore the sub-CPU D0 observation below is debugger evidence only, not an IP-entry test.

## Interpretation and next action

**Verified by execution:** both emulators loaded the owner-supplied EU BIOS and displayed its UI while given the same ISO/CUE image. BlastEm progressed to the CD player after Start. The Genesis Plus GX still frame alone cannot rule out a later response to Start, and that core run did not expose CPU state. **Verified by execution:** the ISO header declares a 0x7800-byte SP at disc offset 0x800, but all 0x7800 bytes are zero. The IP area contains only the eight original marker/loop bytes and zero padding. The image therefore lacks an actual system program and has no security/startup block. **Documented only:** the [Mega CD disc-format specification and security bulletin](https://gist.github.com/akiyan/a90d1e7d41ce89c532f29cafc356ccc2) describe the IP/SP layout and a security block; an independent [homebrew boot account](https://clownacy.wordpress.com/2023/10/11/clownmdemu-booting-sonic-cd/) identifies IP as main-CPU code and SP as sub-CPU code. **Hypothesis:** either missing component could block BIOS handoff; the exact decision path remains untraced. **Unsupported:** successful original-code BIOS handoff, hardware compatibility, Word RAM/ASIC timings, or hardware-equivalent frame pacing.

**Next action:** build an original SP with a valid header/callbacks and investigate a lawful, independently authored startup path. Require a main-CPU IP marker breakpoint and an independent emulator pass before Phase 0 review. A dedicated Word RAM/ASIC/VDP synthetic test follows after boot. The renderer gate remains closed.

## Follow-up: original SP stub, same day

**Hypothesis:** supplying a valid original SP module may allow the BIOS to launch the disc without a proprietary security/startup block. **Expected evidence:** main-CPU IP breakpoint hit and BIOS screen replaced by the program. **Result:** `FAIL` in the observed BlastEm sequence; Genesis Plus GX remained at the BIOS start screen (`INCONCLUSIVE` for launch after Start). **Documented only:** the [SP module-header description by an independent homebrew developer](https://board.mddc.dev/threads/sega-cd-general.24/) describes the 32-byte module header and callback table; the source here was written independently using that layout.

**Verified by execution:** parent source revision `175e6f2dea8d37171fba7a165d85fcc04cfbfa60` plus uncommitted follow-up changes; same macOS x86_64 host, GNU m68k binutils 2.47.20260726, Python 3.14.8, BIOS checksum and emulator binaries described above. `sh scripts/build-smoke.sh` assembled `src/smoke/sp.S`, and `m68k-elf-objdump -d build/smoke/sp.elf` showed the original initializer's `D1 = 0x53503030` (`SP00`) marker.
