# 2026-10-17 reference disc boot control

**Question/hypothesis:** can the existing EU BIOS/BlastEm setup reach a main-CPU initial-program (IP) breakpoint with a supplied working disc, and is the smoke image's 2048-byte sector format responsible for its fall-through to CD PLAYER? **Expected evidence:** the reference reaches main-CPU PC `0xff0000` with the same BIOS, debugger command, and Start input; a 2048-byte data-track conversion also reaches it. **Result:** reference boot handoff `PASS` in BlastEm, including the 2048-byte conversion; smoke handoff `FAIL` in the matched observed sequence; Genesis Plus GX CHD load `PASS`, game handoff after Start `NOT RUN`; physical hardware `NOT RUN`.

## Provenance and setup

**Verified by execution:** source revision `ecfecb4` before this report, host macOS 26.6.2 (25G83), x86_64. The owner-supplied `REF/Sonic CD (Europe).chd` is a CHD v5, SHA-256 `49d648b78789e40fe6a2e9eaf927d85862cb38b51761eba995e2ed2628056988`; `chdman verify -i 'REF/Sonic CD (Europe).chd'` reported successful raw and overall SHA-1 verification. Its provenance beyond the owner's supplied file and internal checksum is **unsupported**. It remains under ignored `REF/` and no disc data, images, or commercial code from it are tracked.

**Verified by execution:** `chdman` 0.289 came from the [Homebrew rom-tools 0.289 formula](https://formulae.brew.sh/formula/rom-tools). `chdman info` reported one MODE1_RAW data track followed by 34 audio tracks, 607,368,384 logical CHD bytes, and `cdlz`, `cdzl`, and `cdfl` compression. `chdman extractcd -i 'REF/Sonic CD (Europe).chd' -o /private/tmp/pd-ref-converted/reference.cue -ob /private/tmp/pd-ref-converted/reference.bin` made a temporary local BIN/CUE; BIN SHA-256 `d9f2e312e4af888ba200a3c2845a199bc089cd4da480d70ed49204ffde023ac7`. BlastEm 1.0.0 reported `Unsupported compressor type cdlz` when opening this CHD directly, so its CHD run is **FAIL** for this file/codec and was not used as a boot result. No upstream emulator files were modified.

**Verified by execution:** the first data track was converted locally from 55,098 MODE1/2352 sectors by retaining each sector's 2048-byte user-data region (bytes 16–2063) in `/private/tmp/pd-ref-converted/reference-mode1-2048.iso`. It is 112,840,704 bytes, SHA-256 `2e12056db4533d1c540224f61c2f8484b96e1f6e5950526a7d144e379d7cc5e9`, with a matching MODE1/2048 CUE SHA-256 `6c046ad03c5a3e6761a2d880c13efff34d6d5d5c383c6b0ff86518cdbc70e573`. This conversion contains only the temporary local first data track; it was not added to the repository. The project smoke ISO SHA-256 was `8baed93a269c2b1c55f6d006da768eb86aba353a8b32e12c37383f34787ec52d`.

## Matched debugger test

**Verified by execution:** BlastEm 1.0.0 from the official macOS x86-64 archive (SHA-256 `2315f5f32b8400b4c56980b87043516ac9ec22aac5fdb9d3bdb97c2b236da221`) used the same owner-supplied EU Model 1 v1.00 BIOS in both runs (SHA-256 `16735df92fcc1d0fc6a1eced244867e95281c5006340926082b74e363e073dc4`). The reference command was `script -q /private/tmp/pd-ref-boot-m1.txt /private/tmp/pd-blastem-eu-test/blastem -r E -d /private/tmp/pd-ref-converted/reference-mode1-2048.cue`; the smoke command differed only in transcript path and final image path (`/Users/murilo/repos/PowerDriftCD/build/smoke/smoke.iso`). Both interactive runs used `breakpoint 0xff0000; frames 600; binddown "gamepads.1.start"; frames 5; bindup "gamepads.1.start"; frames 1200; print/x pc`. The input sequence is explicit; no random seed was used. The `frames` arguments are emulator-requested frame advances, not measured hardware pacing, and a breakpoint may stop an advance before its requested count completes.

**Verified by execution:** the reference run printed `68K Breakpoint 0 hit` and `pc: ff0000` after Start. The ignored raw transcript is `build/evidence/reference-control/blastem-model1-boot.txt`, SHA-256 `c13a15e2a7dbb86ce6245af13d6753c3d7effdc0fb8041e6e77b72dd0b892bfa`. The smoke run did not hit; after the same bounded sequence `pc: 43b4`, and `build/evidence/reference-control/smoke-cd-player.png` shows CD PLAYER (SHA-256 `4651804f851ecaa5b33a025c156ab4acc4ea8fade776fe723c8114c8f2c572d6`). Its ignored raw debugger transcript is `build/evidence/reference-control/blastem-model1-smoke.txt`, SHA-256 `27895cbca58b5c5efe17b10af4a79cd3a3fcb0a9d0951e21d65e1e1ac068a515`. No CPU/ASIC cycle counter or physical-hardware measurement was obtained.

**Verified by execution:** the raw 2352-byte-sector reference also hit main-CPU PC `0xff0000` under EU Model 2 v2.00 in one BlastEm run. A later 600-frame Model 2 run had not reached the breakpoint by its limit, so a fixed frame bound for that BIOS is **unsupported**. The matched Model 1 comparison above used Start explicitly and is the acceptance control.

## Independent core and structural comparison

**Verified by execution:** RetroArch 1.22.2 with Genesis Plus GX loaded the original CHD using the EU Model 2 v2.00 BIOS. The run used the isolated PAL config with `pause_nonactive = "false"`, `--max-frames=600 --max-frames-ss`, and the same core binary as the [earlier BIOS check](2026-10-16-bios-backed-emulator-check.md). Exit status was zero; the raw log is ignored at `build/evidence/reference-control/genesis-plus-gx-reference.log`, SHA-256 `fbd58de0e6b316c5af1a50be9835a67420bd52c3cc7b2ef19c06362903a5c438`. The frame-600 capture still showed the EU Model 2 BIOS `PRESS THE START BUTTON` screen; Start input was **NOT RUN** in Genesis Plus GX because macOS denied automated keystrokes. This core run verifies CHD loading and BIOS display, not game handoff. The [RetroArch network interface](https://docs.libretro.com/development/retroarch/network-control-interface/) was reviewed but its documented commands do not include a normal gamepad Start press. The attempted AppleScript keypress failed with `osascript is not allowed to send keystrokes (1002)`.

**Verified by execution:** reading only both images' system-ID fields showed the same `SEGADISCSYSTEM` identifier. The reference header declares an IP extension at `0x800` of size `0x800`, and SP at `0x1000` of size `0x7000`; the smoke header declares IP at `0x200` of size `0x600`, and SP at `0x800` of size `0x7800`. The reference's first-sector IP region contains 1,439 nonzero bytes, while the smoke's contains eight. These are layout and occupancy observations, not reproduced reference code. **Documented only:** the [Mega CD disc specification and security bulletin](https://gist.github.com/akiyan/a90d1e7d41ce89c532f29cafc356ccc2) explain the expanded IP layout associated with the region-specific security program.

**Inference from the matched runs:** both the EU Model 1 BIOS/debugger configuration and MODE1/2048 data-track format can reach a real disc's IP. The smoke's failure is therefore in its boot content or layout, not explained by those two factors alone. **Hypothesis:** its absent accepted security/startup block is the leading cause; the exact BIOS rejection branch remains **unsupported** because it was not traced. Do not copy the reference's boot code or commercial assets into the smoke image. Phase 0 remains no-go for renderer work.
