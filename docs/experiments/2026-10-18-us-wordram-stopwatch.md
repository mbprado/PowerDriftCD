# 2026-10-18 U.S. Word RAM stopwatch feasibility

**Question/hypothesis:** can the Sega CD stopwatch provide repeatable emulator-side observations for the existing sixteen-command 2M Word RAM exchange? **Expected evidence:** all sixteen data checks still pass, the main CPU records sixteen nonzero stopwatch deltas and one whole-batch delta, and a second boot with the same BIOS reproduces the result. **Result — verified by execution:** `PASS` in BlastEm with the owner-supplied U.S. Model 1 and Model 2 BIOS files. This measures an end-to-end command, ownership, callback, polling, and data-check path in the emulator. It does not isolate a hardware handoff latency or measure host wall-clock speed.

**Documented only:** Sega's [Mega-CD Software Development Manual](https://segaretro.org/images/archive/6/6f/20190509144929%21Mega-CD_Software_Development_Manual.pdf), held locally in ignored `REF/`, describes the shared `$A1200C`/`$FF800C` stopwatch as a 12-bit counter with a nominal 30.72 µs tick. The sub-CPU clears the timer by writing zero to `$FF800C`; the main CPU reads it at `$A1200C`. The [hardware manual](https://segaretro.org/images/5/51/Mega-CD_Hardware_Manual.pdf) also describes the timer. [BlastEm's published source](https://www.retrodev.com/repos/blastem/file/62a53c052d9b/segacd.c) shows a 4096-count stopwatch driven by 1536 emulated 50 MHz clocks per tick; that source revision is corroborating documentation, not proof of the exact implementation in the pinned 1.0.0 binary. The experiment uses main-side reads and does not reset the BIOS's timer.

**Implementation:** `scripts/build-wordram-timer.sh` assembles the previously passing [sixteen-handoff test](2026-10-18-us-wordram-repeat.md) with `WORDRAM_TIMER_TEST=1`. After 2M mode setup and before the first numbered command, the IP stores a batch start reading. It reads `$A1200C` before each transaction and again after the returned data passes both checks, storing each 12-bit modular difference in a sixteen-word table in IP RAM. It also stores the sum of those sixteen differences and a separate modular whole-batch difference. The per-transaction interval includes seeding Word RAM, setting DMNA, requesting INT2, sub-CPU validation and writes, RET, status polling, main-CPU verification, and the measurement reads. The batch interval additionally includes loop bookkeeping between samples. The code reports raw ticks; any conversion to time uses the manual's nominal tick duration. A 12-bit subtraction cannot reveal an unseen complete wrap, so these are modulo-4096 observations rather than independently validated absolute elapsed times.

**Interpretation — verified by execution for tick counts; documented only for nominal duration:** the raw Model 1 batch reading was 51 ticks in both boots, and the raw Model 2 reading was 52 in both. At the documented nominal 30.72 µs/tick, those modulo intervals correspond to 1,566.72 µs and 1,597.44 µs, respectively, if no full counter wrap occurred. The one-tick difference is at the measurement resolution and does not establish that one BIOS or Sega CD model is faster. The 48-tick sum of separately rounded intervals differs from the 51/52-tick whole-batch reading because the samples exclude some loop work and each interval is quantized independently. No claim about physical console timing follows from these emulator readings.

**Limits and next action:** this is an exploratory timer-feasibility result from one emulator and two boots per BIOS. Stopwatch quantization, BIOS activity, and the unobservable possibility of a complete 12-bit wrap constrain interpretation. An independent emulator, Linux, headless, and physical-hardware run are `NOT RUN`; physical testing is deferred until the owner explicitly requests it. The private image uses locally held startup bytes; the original-only ISO has no verified boot. Future measurements should use a longer, bounded batch with explicit wrap handling and separate control-loop cost before selecting a performance architecture. The renderer remains behind the Phase 0 review gate.
