# 2026-10-19 U.S. Model 2 paired Word RAM phases

**Question/hypothesis:** can equal-length, similarly sampled batches separate the composite costs of timer bookkeeping, a sub-CPU level-2 request/reply, 2M Word RAM ownership transfer, and a checked two-word exchange in BlastEm? **Expected evidence:** every phase completes 2,048 iterations with its expected reply or data, the 12-bit stopwatch accounting handles wraps, two forward-order boots reproduce totals, and reversing phase order exposes any order effect. **Result — verified by execution:** all four phases passed in two forward-order runs and one reverse-order run under the owner-supplied U.S. Model 2 BIOS. This is an emulator-side comparison of complete code paths, not an isolation of individual hardware latencies.

**Documented only:** Sega's [Mega-CD Software Development Manual](https://segaretro.org/images/archive/6/6f/20190509144929%21Mega-CD_Software_Development_Manual.pdf) and [hardware manual](https://segaretro.org/images/5/51/Mega-CD_Hardware_Manual.pdf) describe the main-side `$A12000` sub-CPU interrupt request, `$A12002/03` 2M Word RAM control, and the shared 12-bit `$A1200C` stopwatch with nominal 30.72 µs ticks. The earlier [long-batch experiment](2026-10-18-us-wordram-long-batch.md) demonstrated a 2,048-exchange path with wrap accounting but had only a timer-bookkeeping control.

**Method:** `scripts/build-wordram-paired.sh` builds a private U.S. two-track image from independently written IP/SP code, the ignored owner-authorized startup prefix, and generated silence. After the SP callback establishes 2M mode with main ownership, one shared `run_batch` loop and timer sampler execute these 2,048-iteration phases: (1) timer reads, command-number calculation, and loop bookkeeping; (2) main command write, INT2 request, and matching sub-CPU reply without Word RAM transfer; (3) the same request/reply plus main DMNA, sub RET, and ownership polls without shared-RAM data access; (4) the same ownership round trip plus two seed writes, sub validation/transform, and main verification of both returned words. The sub-CPU replies are command-specific, so a stale status cannot satisfy the next command. A mismatch leaves `P4ER`, the phase and command in main RAM; success leaves `P4OK` in D3 and `$0800` for every phase count.

**Timing method and limits:** each phase uses the same `timer_reset`, two `timer_sample` calls per iteration, and one final sample. Each sample adds its 12-bit modular gap to a 32-bit total, counts observed counter decreases, and records the largest gap. The phase variants necessarily execute different main/sub-CPU instructions and polling paths, so subtracting neighboring totals reports a *composite path difference*, not a calibrated interrupt, Word RAM switch, or memory-operation latency. The phases also execute sequentially; `reverse` compiles the same handlers and SP with their call order reversed. One complete, unseen 4,096-tick lap between adjacent reads would alias; the maximum recorded modular gap cannot rule that out independently. No in-program timeout bounds a stalled BIOS or callback.

**Additional raw checks — verified by execution:** all runs ended at PC `$FF0742`, D3 `P4OK`, four counts `$0800`, failure command/phase zero, and main memory mode `$2A01`. Observed wraps for forward runs were 0/2/2/3 and for reverse 1/2/2/2 in table order. Largest modular gaps were 2/15/16/17 ticks forward and 2/15/16/16 reverse. For every phase in all three logs, `elapsed = 4096 × observed_wraps + final_reading − first_reading`; this arithmetic check passed. The reverse order changed each non-control total by at most 23 ticks across 2,048 iterations. The results establish repeatable emulator path ordering for this code and BIOS, not a console-performance budget. **Documented only for scale:** the manual gives 30.72 µs per emulated stopwatch tick; no host wall-clock or stock-hardware speed was measured.
