## Documented capabilities and limits

**Documented only:** [MAME's Lua interface](https://docs.mamedev.org/luascript/index.html) exposes emulated-device state and program-memory reads, with `-autoboot_script` for startup scripts and frame callbacks. Its [input API](https://docs.mamedev.org/luascript/ref-input.html) provides `field:set_value` for digital and analog overrides. [Debugger Lua](https://docs.mamedev.org/luascript/ref-debugger.html) requires debug mode for debugger functions. [Command-line recording and playback](https://docs.mamedev.org/commandline/commandline-all.html) exist, but MAME cautions that playback can desynchronize and recommends matching configuration/NVRAM. Whether these facilities work together for this Power Drift set is **unsupported**.

**Documented only:** MAME's [Sega Y-Board driver](https://github.com/mamedev/mame/blob/master/src/mame/sega/segaybd.cpp) lists Power Drift and describes Y-Board devices and ROM regions. The current source also notes Power Drift/clones lockup issues after an m68k rewrite. That is a concrete risk for choosing a MAME version; it is not evidence that this local set will fail. Pin the exact MAME release or source commit used for any future run rather than treating the moving `master` driver as a stable specification.

**Documented only:** [REA](https://github.com/morluto/rea) can connect an agent to an existing Ghidra native-analysis installation through a local MCP server; its setup requires Node/npm and changes agent configuration. [Ghidra](https://github.com/NationalSecurityAgency/ghidra) is the proposed static-analysis engine. **Unsupported:** an operational REA/Ghidra integration on this host, 68000 analysis of these local ROMs, or any routine/track-data identification. Do not run REA's setup command or install a large framework until MAME produces a useful, reproducible observation to correlate with code.

## First reproducible arcade test

**Hypothesis:** a pinned macOS MAME build and the ignored local set can produce two matching runs of one early, visually identifiable section with fixed controls. **Dependencies:** select and inspect a specific MAME release, obtain its official macOS build without downloading ROMs, confirm its `pdrift` set requirements and input labels, and keep all emulator output/configuration outside tracked files. First run `-verifyroms` against the owner-held set; treat any missing/incorrect set as a precise blocker. If it passes, launch Power Drift with a fixed configuration and explicit input script or recorded input, reach the same early section twice, and capture frame-indexed screenshots plus a bounded, raw memory snapshot from each run. Include a no-steering or fixed-steering control run. Avoid calling any changing word “curvature,” “camera X,” or “speed” until it correlates with controlled visual/input changes and with code or data references.

**Expected evidence:** MAME version/build hash, host, ROM-set identifier and private checksum record, launch flags, input schedule, NVRAM/configuration state, frame count, raw log paths and hashes, screenshot/frame hashes, and a two-run comparison. A matching playback file alone is insufficient: confirm the displayed section and selected memory observations agree. Keep raw RAM dumps, commercial graphics, ROM-derived bytes and recordings private; any tracked report should contain original descriptions and non-reconstructive summaries. If the driver locks up or inputs cannot be replayed, record the exact frame/condition and stop this test rather than inferring track data.

**Next bounded analysis — hypothesis:** once a repeatable section exists, compare memory changes under fixed versus altered steering and at the same frame on repeated runs; use debugger write/read traces to identify candidate state. Only then bring in Ghidra/REA to link candidate addresses to 68000 code and track tables. Sprite/palette viewer evaluation can wait until the road/camera observation is established. This avoids an open-ended disassembly campaign before the first useful sample.

## Handoff to the Sega CD pipeline

**Verified by execution in prior Phase 1A/Phase 2 tests:** the [five-word interface](2026-10-20-live-road-camera-commands.md) accepts a new curve-table phase, ridge-table phase, signed bank, horizon and texture offset for each 64×64 road update. The [128×64 build](2026-10-20-wide-live-road-pipeline.md) kept that interface and sustained 30 Hz in three BlastEm Model 2 runs. These are synthetic test packets; no arcade data has passed through the interface.

**Preliminary hypothesis:** an offline adapter could map a recovered short arcade camera sequence into those five controls, providing a useful first visual comparison without changing the renderer. **Unsupported:** that the five controls represent absolute camera position, arbitrary curvature profiles, true elevation/occlusion, continuous pitch/roll, vehicle-relative position, or the full arcade track. The current curve/ridge tables and narrow value ranges may lose degrees of freedom. Define an input/output error measure against one recovered section before proposing additional command words. Do not modify the existing interface on the basis of the Y-Board's internal organization alone.

**Decision:** Phase 1B can proceed independently while Phase 1A/Phase 2 synthetic graphics tests continue. This report establishes a tool and experiment plan only. Its first milestone remains one reproducible arcade track/camera sample, not a complete reverse engineering of Power Drift. Physical Sega CD testing, original-only disc boot and stock-hardware performance remain separate open questions.
