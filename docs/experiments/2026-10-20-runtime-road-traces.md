# 2026-10-20 runtime road-trace construction

**Question / hypothesis:** can the sub-CPU build the 64 ASIC trace rows during each update, rather than copy a complete host-generated trace table, while preserving the [road prototype's](2026-10-20-perspective-road-prototype.md) image and 30 Hz cadence? **Baseline — verified by execution:** the earlier precomputed-trace image completed 60 checked 64×64 updates with two-VBlank intervals of 1,086–1,087 emulated stopwatch ticks and no upload misses in three U.S. Model 2 BlastEm boots. **Expected evidence:** the same 60 output checksums, a matching final screenshot, 59 successive intervals of 1,085–1,088 ticks, no VBlank upload misses, and a separate trace-construction timing window.

**Result — verified by execution:** the initial runtime-trace implementation with separate checksum and staging passes displayed the correct image but missed all 59 cadence deadlines: updates were 1,629–1,630 ticks apart, about three VBlanks or 20 Hz. Combining checksum verification and main-RAM staging into one pass restored 30 Hz. Three independent U.S. Model 2 boots of the combined image produced identical 60-frame records, all expected output checksums, 59 two-VBlank intervals, and no VBlank upload misses. The same image reached the 60-update completion marker under U.S. Model 1, and its final screenshot matched the Model 2 and precomputed baseline screenshots byte for byte. These are BlastEm L1 observations; no physical Sega CD was tested.

## Method and scope

**Verified by execution:** the host generator now emits 24 compact camera states of 132 bytes each (3,168 bytes total), compared with 24 full 512-byte trace tables (12,288 bytes). Each compact state holds a bank value, horizon, frame offset, and 64 pairs of signed curvature/ridge samples. The sub-CPU computes depth, scale band, source X/Y starts, and X/Y steps for all 64 trace rows before triggering the ASIC. The generator checks its integer expansion against every original trace row. At runtime, the main CPU still checks an additive sum over all 1,024 output words before displaying the 2,048-byte image with staged VDP DMA.

**Important limit — unsupported:** this is partial runtime trace construction, not arbitrary camera mathematics on the sub-CPU. Curvature and ridge samples still come from 24 host-generated states. The output sum could miss compensating pixel errors, although the final displayed screenshot also matched the baseline byte for byte. A free-form runtime camera and a larger viewport remain untested.

**Timing interpretation — verified by execution:** the 12-bit Sega CD stopwatch is emulated by BlastEm; each listed window is bounded below one 4,096-tick wrap. The diagnostic image became ready after the next VBlank boundary (about 543 ticks after the prior one), so the existing two-VBlank wait loop displayed at the following VBlank. Combining verification and copying removes the second 1,024-word read pass. The combined 167–168-tick window includes both checksum work and staging; it is **not** an isolated copy cost. The trace window includes the timer reads and trace construction. The ASIC trigger-to-busy-clear median remained 97 ticks in the combined runs. No main/sub-CPU cycle count or stock-hardware duration is inferred from these stopwatch observations.
