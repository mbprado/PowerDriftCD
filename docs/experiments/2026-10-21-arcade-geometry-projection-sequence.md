# Phase 1B: a bounded arcade geometry and projection sequence — 2026-10-21

**Question / hypothesis:** can consecutive samples from the [identified ROM-backed geometry table](2026-10-21-arcade-rom-geometry-to-road-image.md) and a consistent fixed-point transform account for several adjacent projected object coordinates, under centered and steered inputs? **Baseline:** the private callback-950 Power Drift state, three established steering replays, and the earlier Y-sprite bitmap/affine correspondence. **Acceptance:** check ROM samples against active object fields over multiple callbacks; reconstruct the main-CPU projection using its documented emulated arithmetic devices; verify the input timing at execution; compare with screen evidence without treating a color boundary as a decoded track edge. **Result — PASS for the bounded projection, verified by execution in MAME:** 396/396 sampled source-coordinate triples matched their ROM table triples, and an independent fixed-point replay matched 180/180 subsequent X/Y output-coordinate pairs exactly. The existing bitmap-to-screen boundary method matched 81/81 samples on newly captured screenshots. This is a short reference window, not a decoded complete track or camera trajectory.

## ROM sample and projection checks

**Verified by execution:** at every one of 11 callback snapshots and 12 selected depths, the three active object source fields equal the three words read from the ROM table address calculated from that object's depth: `(source+$18, source+$1A, source+$16) = (sample0, sample1, sample2)`. This held for **396/396** rows across all three steering conditions. The 12 geometry tuples and table addresses were also identical at corresponding callbacks when each steered run was compared with center (**264/264** comparisons). The selected object series is fixed over this short window; its projection changes with live parameters. The triples are private raw reference data, so the CSVs remain ignored. Their SHA-256 hashes are center `fd379ed233b808032367c6eb16644e8ad3e1042bbe22d9f21dce0519ab6d80b3`, left `7fdf094774a71c3a6f9fee34b28d1dc320a5b530b6008677069f15155bb9fe52`, right `11f1b0a0e4bd5899ddb7e2804ec7e308cf8d625be4559f91486d60d8ee4c4b1c`.

**Documented only:** the pinned [MAME Y-Board CPU map](https://raw.githubusercontent.com/mamedev/mame/mame0289/src/mame/sega/segaybd.cpp) maps `$080000` to the main-CPU multiplier and `$084000` to the divider; the [MAME arithmetic-device implementation](https://raw.githubusercontent.com/mamedev/mame/mame0289/src/mame/sega/segaic16_m.cpp) describes signed 16×16 multiplication and signed 32÷16 division. **Verified by execution:** private main-CPU disassembly around `$033D56–$033E68` uses two signed, table-coefficient rotations with arithmetic `>>9`, a `$20000` numerator divided by transformed depth plus `$80`, and signed final multiplications with `>>10`. `tools/phase1b_projection_replay.py` reproduces those operations with explicit 16-/32-bit wrapping and the observed screen-Y offset. This is an independently written analysis model of MAME-observed execution, not original arcade code in the repository.

**Verified by execution:** the game's output coordinate at callback `f+2` corresponds to geometry and most shared inputs captured at even callback `f` for `f=960,962,964,966,968`. One shared horizontal projection offset at `$0C0098` changes just before the projection pass, so the value captured at `f+2` is the input actually used. This alignment was checked separately at the selected object's `$033D1E` entry in center/left/right debugger traces through callback 973: the five execution-time offsets and five output X words match the corresponding `f+2` snapshots. The ROM coefficient lookup indices are separate angle-like inputs; the `$0C0098` offset must not be labeled an identified camera angle.

Using that time-aligned input, the replay predicted **60/60 X/Y pairs per condition, 180/180 total**, across five update steps and 12 objects. No fit parameters were estimated from the observed output coordinates. Supplying only the earlier end-of-callback offset instead produced one-pixel X residuals for some steered objects; resolving that sampling error is why the execution-time trace matters. This is offline reconstruction given the later live input, **not** a forecast of future steering or camera motion.

## Visible boundary and limits

**Verified by execution:** rerunning `tools/phase1b_ybitmap_sequence.py` on the new center/left/right bitmap and screenshot captures again made 81/81 mapped first-opaque source pixels agree with first non-sand screen pixels across bitmap frames 960–968 and screen rows 162/165/168. The 81/81 agreement validates bitmap-to-screen mapping of this *visible alpha/color boundary*. It does not prove all sampled pixels belong to one physical track edge.

**Inference from verified execution:** this bounded chain now connects ROM geometry samples to active object coordinates, then through the main-CPU fixed-point projection; one prior controlled coordinate intervention connects the selected record to a Y-sprite road-height image change, and the Y-bitmap affine mapping matches the observed screen boundary. **Unsupported:** a unique one-to-one mapping from each of the 12 ROM samples to a specific visible boundary pixel on every frame, a fully decoded camera pose, curvature/elevation units, or a Sega CD five-word adapter. The Y-sprite writer, sorting, occlusion and image content still intervene between projected main-CPU coordinates and the chosen screen boundary. No second arcade emulator, Sega CD test, performance measurement or physical hardware test was run for this experiment.
