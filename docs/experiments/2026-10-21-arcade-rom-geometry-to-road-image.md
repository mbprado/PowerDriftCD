# Phase 1B: ROM geometry to one road-height sprite strip — 2026-10-21

**Question / hypothesis:** is the previously traced `$0C1C80` object sourced from a depth-ordered geometry table, and does changing its pre-projection coordinate alter the same visible Y-sprite strip without confusing it with another object? **Baseline:** the callback-950 private state and the [main-record-to-screen trace](2026-10-21-arcade-sprite-record-provenance.md). **Acceptance:** identify the object's source fields and writer; compare a bounded object list under centered/left/right steering; perturb one pre-projection field while preserving sprite identity; include sham and repeated runs. **Result — partial PASS, verified by execution in MAME:** `$0C1C80` is the first active record in a 116-entry, depth-ordered object list. Its coordinate fields were populated by the main CPU from a ROM-backed six-byte-per-sample table selected for the running game. A small coordinate change at projection time moves the same Y-sprite entry and a visible road-height boundary. **Unsupported:** the table's complete track format, the object's formal gameplay name, or a decoded camera/curvature/elevation trajectory.

## Object identity and ROM source

**Verified by execution:** a conditional main-CPU breakpoint at projection entry `$033D1E`, limited to output list base `A0=$0C9800`, observed 116 active entries in each center/left/right replay. The first was `A5=$0C1C80`, with depth-like field `(A5+$3E)=$3200`, source coordinate words `(A5+$16)=$1B75`, `(A5+$18)=$0657`, `(A5+$1A)=0`. The next records were `$0C1CC0` at `$3400` and `$0C1D00` at `$3600`, each `$40` bytes apart, and the last observed was `$0C3940` at `$FC00`. All 116 addresses and these four fields matched exactly across the three steering replays. Other projected fields, including the target's output X, did respond to steering. The record's first long word changed with projection/depth and is **not** a proven persistent gameplay identifier; the address and geometry tuple identify it only within this bounded replay.

**Verified by execution:** a cold-boot watch at `$0C1C96–$0C1C9F` showed the main CPU writing the target's three source coordinate words at the routine near `$033B60–$033B68`. At `$033B02–$033B22`, it derives a table offset from the record's `$3200` depth and a pointer at `$0CEB00`. The selected pointer was `$01C9C8`; the target sample was at `$01D328`, exactly `$0960` bytes later. `$0960 / 6 = 400`, matching `$3200 / 32 = 400`. The three 16-bit sample values at that location fed the coordinate words above after the routine's local transform. A separate cold-boot watch saw the main CPU replace an earlier table pointer with `$01C9C8` near PC `$03867E` during game setup; the selector routine reads a descriptor chosen using game-state fields. [MAME's Y-Board main-CPU map](https://raw.githubusercontent.com/mamedev/mame/mame0289/src/mame/sega/segaybd.cpp) **documents only** `$000000–$07FFFF` as ROM, so `$01C9C8` and `$01D328` are ROM-space addresses in this emulation. The control-point interpretation is an **inference from verified execution**; the arcade's names, scale and track-section index are **unsupported**.

**Verified by execution:** the projection routine near `$033D56–$033E58` combines per-object `$16/$18/$1A` fields with a shared parameter block at `$0C0080`. Main-CPU watches found steering-responsive writes to that block near `$033980`, `$034842`, and `$03484C`; the latter two are derived from another RAM record at `$0C0840`. At the selected object's projection entry, the source coordinate words remained identical for all three steering conditions, while shared block values and projected outputs differed. This separates stored geometry from a live, steering-responsive transformation. Calling `$0C0080` a fully decoded camera state is still **hypothesis**; no independent camera pose has been recovered.

## Controlled projection change

**Verified by execution:** at the selected object's `$033D1E` entry, a debugger action temporarily changed only `(A5+$16)` from `$1B75` to `$1B95` for the `$0C9800` output-list pass, restoring `$1B75` before the list copy at `$033E84`. The same-value `$1B75→$1B75` run was the sham. The source sprite stayed at Y-sprite RAM offset `$E630`, retaining its ROM graphic offset `$3888`, bank and linked-list position. Only six bytes of the 65,536-byte Y-sprite RAM snapshot differed; the `$E632` X field moved `$693→$696`. [MAME's Y-sprite field layout](https://raw.githubusercontent.com/mamedev/mame/mame0289/src/mame/sega/sega16sp.cpp) **documents only** the second word's low 12 bits as X and the fourth word as a sprite-ROM offset. The sham matched normal descriptor RAM, bitmap and screenshots.

## Interpretation and next test

**Inference from verified execution:** the source table, depth ordering, stable coordinates under steering, and the intervention's broad road-height image effect make this a strong *road-geometry candidate*, not merely a generic sprite X coordinate. **Unsupported:** whether the table encodes the centerline, a road edge, roadside strip, or another path-following surface; the unit scale and coordinate axes; which record is the camera pose; and whether the Sega CD five-word camera interface can represent this arcade sequence. The present result is L1 emulator evidence, not arcade-hardware or stock Sega CD validation. A second emulator and physical hardware were **not run**.

**Next bounded test — hypothesis:** decode a short, consecutive run of ROM table samples together with the corresponding active object records and independent visible road boundaries, then test whether one consistent coordinate transform predicts several adjacent frames. If it does, that sequence becomes a candidate arcade reference handoff. Keep the existing Sega CD camera interface unchanged until a measured degree of freedom is missing.
