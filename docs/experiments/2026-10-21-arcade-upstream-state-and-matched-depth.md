# Phase 1B: upstream state and matched-position steering — 2026-10-21

**Question / hypothesis:** can the state feeding the [shared transform producer](2026-10-21-arcade-transform-producer.md) be traced far enough to compare steering at the same depth-indexed lookup position? **Baseline:** owner-local callback-950 MAME state; deterministic center steering 128 and left/right pulses 64/192 from callback 960; existing private 960–1000 projection and transform traces. **Acceptance:** identify live writers of the position, angle-adjustment, offset-source and lookup-position state; verify the lookup advance against its operand; compare base and adjusted position words only where the exact lookup position agrees. **Result — PASS for this bounded chain, verified by execution in MAME:** 60/60 state/lookup update passes matched; 21 exact-position center/steered comparisons had identical three-word base samples and different final X/Y words. Later steering runs lose exact position alignment, so they are not treated as controlled same-track-position comparisons.

## State-to-transform chain

**Verified by execution:** all watched state writes in these runs came from the main CPU. In each of 20 updates per steering condition, `$034AE4–$034AF0` loaded a three-word base position from a table pointer into the active state. The later `$034C30–$034C48` path changed two position words and wrote the next offset source. The final state X/Y/Z words matched the operands subsequently read by the transform producer in **60/60** updates. The angle-adjustment write at `$034E0A` matched the producer's later signed adjustment in all 60 updates. The offset-source write at one update matched the next update's projection-offset source in all **57/57** observable consecutive pairs. These are emulated CPU events, not physical camera units.

**Verified by execution:** local disassembly at `$034904–$034912` reads a state word, arithmetically halves it, and advances a fixed-point lookup accumulator. The debugger recorded the state word, half operand, old lookup position and write. All **60/60** writes equaled old position plus the observed half operand (modulo 16 bits); the written position matched the following update's read position in all **57/57** available consecutive pairs. The captured value is a *speed-like operand* in this code path, not a calibrated arcade distance or a Sega CD timing value.

The half operand first differed from center at marker 975 on the left and 985 on the right. The next read lookup positions first differed at 977 and 987, respectively, matching that update order. **Inference from verified execution:** the runs begin to sample different positions because this operand changes, so later same-frame visual differences mix steering with lookup progression. The cause of the operand reduction remains **unsupported**; collision, road state, controls and other game rules have not been isolated.

## Exact-position comparison

**Verified by execution:** there are eight center/left and thirteen center/right update markers with exactly equal lookup-position words: **21 matched markers total**. For all 21, the three base table-loaded position words matched center exactly, while the two position words *after* the `$034C30–$034C38` adjustment differed. This isolates a steering-associated adjustment on top of the same observed base sample for that bounded window. The adjusted offset source also differed in all 21 comparisons. A coarser lookup index obtained by clearing the low five bits matched at 12 left and 17 right same-frame markers, but that does **not** establish equal exact position; the result above uses only the 21 exact matches.

**Verified by execution:** the angle-adjustment state differed in 17 of the 21 exact-position comparisons. The conditional late-adjustment counter was written 15 times in the left run and ten in the right, versus zero in center; the [producer trace](2026-10-21-arcade-transform-producer.md) separately observed 14 and nine later translation writes. The extra counter's physical meaning is **unsupported**. The comparison does not prove that the table triple is a decoded track centerline or that adjusted X/Y are literal camera coordinates.

**Unsupported:** one complete real track-section trajectory, calibrated units, a uniquely attributed continuous visible road edge, a five-word Sega CD adapter, original-hardware performance, or a causal explanation for the speed-like operand change. No second arcade emulator or physical hardware was used. **Next bounded test — hypothesis:** correlate this exact-position state chain with one far-depth road-height descriptor and its visible contribution over several consecutive updates, then try an offline private mapping to the existing Sega CD controls. Keep renderer and camera interface unchanged until a concrete visible mismatch establishes a missing degree of freedom.
