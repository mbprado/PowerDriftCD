# Coupled width and lateral road motion — 2026-10-23

**Hypothesis:** the existing five-word live camera interface can animate a wider road's position and width together at 30 Hz, using original precomputed stamp-map geometry for the width profile. **Baseline:** the [static-width 128×64 ASIC road](2026-10-23-wide-asic-road-geometry.md), which passed three U.S. Model 2 BlastEm boots with 89–90-pixel widths at the reference rows and a worst image-ready time of 875 emulated stopwatch ticks. **Acceptance:** preserve that control image byte-for-byte; generate 60 deterministic packets with both width and lateral changes in the host reference; verify 60 ASIC sums, sampled Word RAM words, VDP display, two-VBlank cadence and zero upload misses in three cold boots. **Result — verified by execution in BlastEm 1.0.0: PASS for this synthetic sequence.** This is not an arcade-derived camera trajectory or physical-hardware result.

## Test design and correctness

**Verified by execution:** `runtime-live-wide-motion` keeps 128×64 output, the five camera words, the 2M Word RAM handoff, 4,096-byte main-RAM staging and VDP DMA, and the existing two-VBlank scheduler. The packet sequence uses curve phase `3×frame mod 96`, texture position `2×frame mod 48`, fixed ridge phase `0`, bank `0`, and horizon `4`. The texture-position word moves through an original 16-row stamp map whose road strip is 56, 58 or 60 source pixels wide in a repeating three-row pattern. Its purpose is to model a small precomputed geometry profile along a synthetic forward path. The road uses 15 original stamp variants plus one grass stamp; the sub-CPU copies 2,176 stamp bytes and initializes the 512-byte map for each output. No sixth camera word, new ASIC register, software replacement renderer, or production camera-interface change was introduced. The prior static-width control rebuild retained its exact IP/SP/ISO SHA-256 values `695902119a4b7e55cb19dc30b338ece4c269079c186ddac5b2955838152ea39f`, `9121ed4e0e73efff1ef13a3ca2468d7b258d457e35231dcd996424c623122447`, and `91c1e6ecf4e1f5b0df30b8059fbdefcb9606e139eaa083a81cb76a2bb4fa6e82`.

**Verified by execution of the host reference:** across 60 packets, all 480 road runs at output rows 25–32 are contiguous, **89–96 pixels wide**, and unclipped. At row 28 the distinct widths are 89, 90, 92, 93 and 96 pixels; road center ranges from X=55.5 to X=72.0. Width and center change on the same adjacent update **22 times**. The [per-frame host metrics](data/wide-road-motion-host-metrics.json) record all five command words, the eight row bounds and each 2,048-word expected output sum. This demonstrates coupled motion at the measured-width rows, but the lateral coordinates and width sequence are synthetic and are not matched to a Power Drift arcade turn.

**Verified by execution in BlastEm:** the private image's IP/SP/ISO SHA-256 values are `7310c4d97fe069910a5d4d204105830dd9a4884213f91d8296bdf1995d6aed62`, `3a742ca60144f36fea988605fdc0031496acc9221fa581be4a37a9d81d4b000c`, and `4d48d9f0b50e59c0b90d5a956593fdeabee8e18ace9792d74ed0040ed0c0468a`. All three runs reached `GVOK` (`d3=$47564F4B`, `d6=$3C`) after 60 ASIC outputs passed their expected additive sums. In run 1, the final five command registers held `$0051,$0000,$0000,$0004,$0016`, matching packet 59. Eight sampled final Word RAM words at indices `0,1,63,64,511,1023,1535,2047` matched the host values `$3333,$2223,$2223,$2222,$7777,$7777,$7777,$3333`. Additive sums and eight samples do not establish every output word or exact VRAM contents.

**VDP display — verified by execution:** original-road pixels and visibly different road positions/widths appear in the clean 256×240 BlastEm [intermediate screenshot](data/wide-road-motion-model2-intermediate.png) and [final screenshot](data/wide-road-motion-model2-final.png), SHA-256 `b3529b366a5f57cc2a696c873a4b435f69d451402d251262f7c047015f222659` and `8e58e6cd5c56eb9cc079c91d76e801c3c3a850ee36dc0ebfbf8d15fa65bcd337`. The intermediate capture followed 40 debugger `frames` after IP entry, when `d6=$10`; the final capture followed `GVOK`. An independent [indexed-PNG pixel check](data/wide-road-motion-screen-check.json) found the nonblack viewport exactly at X=96–223/Y=89–152 and **2,607 changed viewport pixels** between captures. At output row 28, the displayed road spans X=26–118 (93 pixels) in the intermediate capture and X=12–103 (92 pixels) in the final capture. The former bounds match both host packets 15 and 16, so the screenshot alone does not distinguish which had just reached the VDP; the latter matches packet 59. This verifies displayed geometry at two points, not pixel-exact agreement or correct display of every intervening update.

**Inference from verified execution:** the worst image-ready time rose by 48 ticks from the previous static-width run, leaving approximately **163 ticks** until the approximately 1,086-tick intended upload edge. Extra stamp/map work, source selection and packet path are combined in the ownership window; this test does not isolate a per-stamp cost. The ASIC busy window reached 204 ticks in some frames, while the 4 KiB staging and upload windows did not grow. The previous static-width data were captured on an earlier date; test order was not varied, although the control image rebuild is byte-identical. This synthetic workload met 30 Hz in BlastEm but does not establish spare capacity for scenery, gameplay or hardware.

**Limitation / unsupported:** this uses texture position to select a precomputed width profile. It shows that this *particular* coupled sequence fits the existing five-word transport; it does not show independent arbitrary width and texture-scroll control, arcade-derived steering widths, a complete road geometry adapter, Model 1 compatibility, a second-emulator pass, or physical-hardware frame pacing. A separate width command should be considered only after a measured arcade camera sequence requires width changes that cannot be represented by track geometry plus the current controls.
