# Phase 1B research throughput plan — 2026-10-23

**Question / hypothesis:** can the existing MAME arcade-reference workflow run more experiments per session without weakening deterministic controls or losing evidence? **Baseline — verified by source inspection and local file audit:** the source-hide runner launches the same callback-950 saved-state sequence separately for each candidate, writes full source RAM and composed-screen captures, then decodes screenshots again during analysis. One recent callback-968 trial contained **143 files**: 18 Y-sprite source dumps (1,179,648 bytes), 34 other source/palette dumps (348,160 bytes), 17 composed screens (490,570 bytes), 66 swap-word files (2,112 bytes), and three other files (60,431 bytes). `du` reported 2.4 MB for that trial. These are local storage measurements, not emulated hardware timing.

**Research policy — design decision:** increase the number and variety of controlled experiments. Optimize repeated setup, capture volume and analysis work *per experiment*; do not limit hypotheses, skip new conditions or replace independent repeats with cached results. Each run or reused artifact must retain its provenance, and every experiment should state which architectural decision its result can inform. Useful throughput measures are time from question to trustworthy result, reproduction effort and decision coverage, alongside host run time and storage.

## Prioritized opportunities

| Priority | Proposed small addition | Expected benefit and evidence needed | Main correctness constraint |
| --- | --- | --- | --- |
| 1 | Thin, opt-in MAME runner with a content-addressed evidence cache | **Hypothesis:** exact repeated trials can avoid a MAME launch; the later [selective-capture benchmark](2026-10-23-phase1b-selective-capture-benchmark.md) measured 4.791–5.370 median host seconds for this one workflow, not a general cache saving. Key the entry by hashes of MAME executable, Lua probe, saved state, owner-local ROM manifest, override bytes, relevant environment values and full command. Store an output manifest with size/hash for every file; reuse only after complete validation. Record cache hit/miss and input digest. | A missing, changed or partial artifact must cause a fresh run. New inputs and deliberately independent repetitions always execute MAME. Never use a cache hit as an independent repeat or claim a new emulator execution. Keep cache and all provenance under ignored `build/private`; check the ROM manifest against owner-local files when a new cache entry is made. Avoid a broad runner refactor. |
| 2 | Opt-in selective capture profile in the current Lua probe | **Hypothesis:** source-hide trials can retain all screen frames used by the existing causal control while dumping only the Y-sprite RAM at the intervention callback and after the write. This should remove about 1.4 MB and 50 redundant source files from a representative run, plus Lua memory-read work. Compare full and selective trials using the existing analyzer and identical screen/source hashes. Default remains full capture for unknown research questions. | Do not omit earlier screenshots or the exact post-write Y-sprite dump needed to verify the intervention. Include profile name in future cache keys. |
| 3 | One calibrated arcade-versus-Sega CD geometry comparison entry point | **Hypothesis:** reading existing causal edge JSON, an explicit crop/sample calibration JSON and existing host packet/image metrics in one command will replace manual coordinate arithmetic and repeated ad hoc fits. Emit per-row deltas, source hashes, and marked fit versus validation rows. | Calibration is an input assumption, not recovered arcade projection. Never silently fit a camera packet to validation rows or compare unmatched coordinate spaces. No rendering architecture change. |
| 4 | Machine-readable acceptance criteria and regression report | **Hypothesis:** a small JSON spec can assert causal edge checks, prior-screen identity, fit/held-out error limits and image hashes; a report can identify PASS/FAIL/INCONCLUSIVE with a reason. Initially wrap existing analyzers rather than rewrite them. | Missing inputs are INCONCLUSIVE, never PASS. Changed calibration, image or ROM inputs require new provenance. Preserve raw evidence and human-readable reports. |

**Ranking — hypothesis:** exact-run caching has the greatest potential elapsed-time benefit for repeated candidate probes. Selective capture has the smallest implementation and verification surface and benefits every *new* source-hide trial. Geometry/criteria automation mainly reduces analyst time and error; their time savings are not yet measured. A cache should follow after capture-profile semantics are stable so its key can include the profile. The runner should use the project's existing Python standard library and MAME/Lua tooling; no new dependency is justified.

**Status — verified by execution on 2026-10-24:** the [selective capture profile](2026-10-23-phase1b-selective-capture-benchmark.md) and an [opt-in exact-replay cache](2026-10-24-phase1b-evidence-cache.md) have been tested. The cache helps exact repeats but adds input-hashing cost to a first run, so normal independent experiments remain the default. The next proposed improvement is the calibrated geometry comparison; it has not been implemented or benchmarked.

## First bounded implementation

**Planned test:** add an opt-in `road-edge` capture profile to the existing Lua probe and a pass-through option to the source-hide runner. It will preserve full composed-screen captures and the callback's Y-sprite before/after evidence, but omit unrelated source/palette dumps. The current default and all prior scripts remain valid. Run full and selective versions of the *same* callback-968 `$A600`–`$A6FF` intervention from the same saved state, analyze both, compare screen and source checksums, and measure host elapsed time plus bytes/files written. Repeat in varied order if the timing difference is small. This first change does not implement the cache, geometry entry point or acceptance schema.

**Acceptance criteria — hypothesis:** both profiles must produce the same Y=152–156 causal flags, identical screen PNG hashes for screens 960–976, and the same callback-968 post-write Y-sprite hash. The selective profile must leave all earlier-screen identity checks possible and reduce files/bytes. A host-time improvement will be reported only as a local workflow measurement, never as arcade or Sega CD speed. If any correctness check fails, retain full capture as the only accepted profile.

**Restrictions — documented only from project rules:** ROMs, BIOS files, proprietary extracts, private saved states and raw screenshots remain ignored under `build/private`. Physical Sega CD hardware is not used. No push, PR, merge or release follows without separate owner authorization.
