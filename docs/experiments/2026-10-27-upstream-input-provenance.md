# Phase 1B: lookup-table and state-word provenance — 2026-10-27

## Question and frozen test

**Hypothesis:** the two RAM tables consumed by the [held-out index predictor](phase1b-static-analysis-feasibility.md) are populated by identifiable main-CPU code, and the preceding `$0C08BA` state update can be predicted from earlier state. **Baseline:** local source `e54299e` on `experiment/perspective-road`; the owner-private `pdrift` ROM set, isolated MAME 0.289 and callback-950 state. The [plan](2026-10-27-upstream-input-provenance-plan.md) froze the cold-boot table watch, the pulse-208 input schedule and the 20-write state test before any target values were read. **Acceptance:** identify writer PCs and verify the final tables against prior snapshots; freeze predictions from pre-write inputs before a separate target replay; require 20/20 exact and callback-aligned results.

## Table producer

**Verified by execution:** a main-CPU write watch from power-on through frame 950 recorded 12,288 writes to `$1FA000–$1FBFFF`. An early clear loop at `$039526–$039534` made 4,096 zero writes across the two 4 KiB tables. The later `$0387CC` loop made 4,096 writes to `$1FA000–$1FAFFE`, and `$03881A` made 4,096 to `$1FB000–$1FBFFE`. A second boot reproduced the same write counts and the same final table bytes. The final frame-950 tables were byte-identical to the callback-960 and callback-1000 snapshots used in the earlier index predictor: SHA-256 `$1FA000` `b76226e2874895a8446f4ee47a7701957d5d07ad1f487ed3584882e5cbeaddac`; `$1FB000` `58026dc7abea35d5336cdbd17dab0dc41714eafb9c8f64e2e9d49643b979f679`.

**Verified by execution of the second boot:** entry breakpoints showed two table-generation rounds, first with the source pointer at `$02CB88`, then at `$01C9C8`. Each round called `$038736` and `$038768`; each call wrote 2,048 words to its respective RAM table. At both entries, `A6=$080000`. The privately assembled, live-MAME-verified main-CPU image and bounded GNU m68k disassembly show that these routines load the source pointer from shared `$0CEB00`, traverse source records at six-byte steps and call a helper that accesses `A6+$4000` registers. The pinned [MAME Y-Board driver](https://github.com/mamedev/mame/blob/mame0289/src/mame/sega/segaybd.cpp) **documents only** `$084000` as the main-CPU arithmetic divider mapping. Together these observations identify the tables as **computed from ROM-addressed source data with hardware arithmetic**, not immutable tables stored directly in ROM. The precise geometric meaning of either table value is **unsupported**; the helper's complete numeric behavior was not reimplemented here.

**Inference from verified execution:** the later `$01C9C8` round supplies the final table content used by the saved-state pilot, because the same output addresses are rewritten in order and the final bytes match that pilot. Why the game selects the two source pointers, and how that selection relates to tracks or game modes, remains **unsupported**. The watched main-CPU range had no writer outside the listed PCs in these two boot runs; writes before script/watch activation or in other game conditions were not tested.

## Earlier state update

**Verified by execution:** an input-only pulse-208 run captured old `$0C08BA` (`A5+$7A`), source `$0C08BC` (`A5+$7C`) and the just-updated sign-control word `$0C08C8` (`A5+$88`) at main-CPU `$034DDA`. The [independent model](../../tools/phase1b_state7a_predict.py) applies the observed 68000 word operations: signed arithmetic half of `$7C`; sign reversal if `$88` is negative; subtraction of old `$7A`; signed clamp to ±`$20`; then wrapped addition to old `$7A`. Its 20 predictions were frozen in private JSON (SHA-256 `4e72a38aad726dbf22fee75e5b076b143759e527053bbfd190cecb5702d94764`) before a separate MAME replay observed the value after `$034E06`. All **20/20** values matched at odd markers 961–999, with zero callback offset or numerical difference. In the exercised window, `$7A` moved from `$0000` to `$FFE5`, `$7C` from `$0000` to `$0037`, and `$88` was negative throughout. The ±`$20` clamp never activated; positive-sign and clamp behavior remain **documented by the local instruction sequence only**, not validated by this replay.

**Inference from verified execution:** the new model moves the predictive boundary one producer step earlier than the prior `$0C00A6` model. It still receives `$7C` and `$88` from MAME at the earlier instruction; their producers and steering relationship are **unsupported**. Neither model directly predicts a camera pose or Sega CD five-word command from raw input. The main-CPU `$034DDA` to `$034E0A` stage is a state update, not an identified physical bank or pitch calculation.
