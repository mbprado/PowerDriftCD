# Phase 1B: controlled low-D3 correction — pretarget checkpoint

**Hypothesis:** at main-CPU `$034FA4`, the low word of `D3` is added to `D0` before the optional `$80/$7E` addition and signed clamp. A guarded register-only intervention at this PC should therefore increase the immediate `$0C0868` (`A5+$28`) output by the injected amount when the other addend is zero and the clamp is inactive. This tests one arithmetic stage, not the natural source of `D3` or a road-camera mapping.

**Baseline and method:** source baseline `fe64179`; isolated MAME 0.289 source `f34f02505e32c1993c6a782b6814232cbfc74e36`, executable SHA-256 `8e4966a8a42e70cba398a8ec62bf3550bef84938bc17946579a69caac11876ba`; macOS 26.6.2, x86_64. Use the private callback-950 state SHA-256 `700b12cf2a60cdb44448877a07ae24395dc77a35b89d69fb2df6a60d27422b6a` with pulse 212. The new `PDRIFT_DEBUG_WATCH=position_d3` probe arms at callback 960, changes only the low 16 bits of `D3` at `$034FA4` with `A5=$0C0840`, logs the `$034FDA` output, and clears both breakpoints at callback 962. The breakpoint register assignment follows [MAME 0.289's documented debugger syntax](https://docs.mamedev.org/debugger/breakpoint.html). ROMs, state and raw logs are ignored/private.

**Verified by execution, development control:** one `+$0001` run at marker 961 logged pre-branch `D0=$FE4400A7`, `D3=0`, timer `$FFFF`, `$80=0`, `$7E=0`; it logged `D3=1` after the breakpoint assignment and wrote `$28=$00A8`. The control used `PDRIFT_POSITION_D3_PHASE=both` and is stored at `build/private/phase1b-d3-dev1/` (`debug.log` SHA-256 `b705e0c6e42382922508928efefd4a05e6e2a8aa566aa2b2409df6d62352dde3`; stdout SHA-256 `251337f004e41583515808c724e5c4fc94dfc313c36429b3ef0af936cfc3369f`). Probe SHA-256 was `52c0c90b1796fb4a690bf2a26c17c955c56d5dc2504f2f0f0c823dea8922d099`; predictor SHA-256 was `d8fc958b8357288d6b52d29ab4355cbf8d1d75c584a662a69c9e9b926d03b948`. The timer field is observed but not assigned a gameplay meaning. The branch action changed no memory directly.

**Frozen prediction before target capture:** `python3 tools/phase1b_d3_correction_predict.py freeze build/private/phase1b-d3-dev1 build/private/phase1b-d3-frozen.json` saved SHA-256 `7dbc2ff0778d913ea9251f0fbefb8f7b2d700109792bdc485a6318197a904d5d`. For a separate `+$0040` run, it predicts post-add `D0=$FE4400E7` and `$28=$00E7` at the first marker-961 write. The expected signed word is within ±$05FF, so this test does not exercise the clamp. Target runs must use `PDRIFT_POSITION_D3_PHASE=output`, hiding pre-branch values from the target trace, and compare the output against this frozen record with the tool's `validate` command. Three independent target MAME runs are planned.

**Acceptance:** the target trace must have exactly one marker-961 output in the armed interval, no input trace, and exact `D0` and `$28` matches in all three runs. A mismatch is a failure to be investigated, not a reason to edit the frozen prediction. No emulator-host speed is treated as hardware timing. BlastEm, other arcade emulators and physical hardware are **NOT RUN** for this branch test.
