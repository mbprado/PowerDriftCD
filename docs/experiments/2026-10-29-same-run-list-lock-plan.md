# Phase 1B: same-run list-lock interval — prerepetition checkpoint

**Question:** did Sub-Y's count write that changed `$0027 → $0028` occur between the main CPU's target-object entry and its list-lock acquisition in the **same MAME execution**? The prior [cross-CPU count result](2026-10-29-shared-list-count-flow-result.md) predicted entry `$0027` and observed copy `$0028`, but its Sub-Y writer evidence came from a separate input run. This test supplies the missing same-run event order; it is a bounded causal timing audit, not a new steering-to-camera model.

**Baseline and acceptance:** source baseline `f5daa44`, branch `experiment/perspective-road`; pulse 124 and the private callback-950 state. Three fresh MAME 0.289 runs should each show, in one debugger log: main target entry at `$0027` with lock clear; one Sub-Y lock acquire, count write `$0028`, and lock release; main lock acquire at `$0028`; then main copy at `$0028`, with no intervening count write after main acquires the lock. The [auditor](../../tools/phase1b_projection_lock_audit.py) checks exact event order, CPU IDs, old lock/count state, written values and stage counts. A mismatch is a failure. These are repetitions of a development observation, not held-out input-schedule predictions.

**Verified by execution, development probe:** a full pulse-124 write trace found the three Sub-Y writes between target entry and main lock acquisition. A filtered probe produced the same ten-event target interval, with debugger/control SHA-256 values `d6ebfba74d063e5e77eba832568d6c53c45aea20ef360e1be0ae2b49ae16ba3b` and `4208d82ead92d11eb2f04b66fc3d770aa6a266b9eff673ef87e6ec6b06d16130`. Filtering unsuccessful TAS polls and stopping capture at callback 962 reduced the private debug log from 324,038 to 38,557 bytes. This is a **composite capture-size reduction**, not an emulator-speed or hardware-timing measurement. No target repetition has been run at this checkpoint.

**Method:** the opt-in `projection_lock_interval` mode watches writes to shared count `$0CFCF0` and lock byte `$0CEB43` in main, Sub-X and Sub-Y program spaces. It logs main PC stages `$033D1E` (entry), `$033E68` (before TAS), `$033E70` (after TAS), `$033E8E` (copy) and `$033E94` (after count increment). Lock-watch conditions retain release writes and TAS attempts where the old lock byte was clear; they omit repeated failed polls. The auditor limits analysis to the first target interval before callback 962. The probe and auditor SHA-256 values are `b2be076d67188153718fd454f706ebea1f08483bce332303ed77c6ac02b38ffc` and `aa9563b39499a401370684d803a8b5a50def93fc4a3970d44ebe2524ee47ba4e`.

**Interpretation limit:** one successful same-run ordering proves what happened in this tested MAME window. It does not predict whether Sub-Y wins the lock on another input schedule, explain the earlier Sub-Y object-selection algorithm, or derive `$0CFE08` buffer selection. A later predictive test should use earlier Sub-Y state and lock timing to predict whether this one-count interleaving occurs, before promoting a frame-start-to-slot model.
