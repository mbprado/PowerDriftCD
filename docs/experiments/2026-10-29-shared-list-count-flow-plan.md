# Phase 1B: shared list count across CPUs — pretarget checkpoint

**Hypothesis:** the first pulse-124 main-CPU `$0C1D00` entry count can be predicted from the reset and prior writes to shared `$0CFCF0`, without reading the count at that object's entry or pre-copy stage. The input-only MAME run watches all three CPU program spaces and exits when the target reaches `$033D1E`. The model accepts exactly one reset to zero followed by a contiguous `1…N` write sequence; it predicts the target-entry count as `N`. This is a count at **object entry**, not automatically the eventual list-copy count.

**Why this scope:** a development pulse-212 main-only watch skipped values. A separate all-CPU watch attributed the missing increments to Sub-Y. A development output probe observed target-entry `$0026` but pre-lock/copy `$0027` at marker 961; a Sub-Y increment occurred between those stages. That establishes a concrete inter-CPU timing risk. The held-out test scores only the earlier count; it records pre-lock/copy values to measure any subsequent change. The development input and output debugger SHA-256 values are `62d1c6e8b500c05a95dbe79dd250520b3cea13c4d0707aa98231ad8328b582b4` and `f70ce7f9a735fbfa41a9ccc5041bf5f07aa0cdd957635b963dbbc4f0982582c0`.

**Baseline and acceptance:** source baseline `57a738b` on `experiment/perspective-road`; owner-private callback-950 state; previously unused steering pulse 124. Three fresh output-only MAME 0.289 runs must each match the frozen target-entry count at the first odd marker 961. A discrepancy is a failed prediction; do not adjust the frozen value after target capture. No cache hit counts as an independent run. The output probe also logs the later pre-lock and copy count/slot for diagnosis, but those are not frozen predictions.

**Verified by execution, input-only:** the callback-960 initial count was `$007E`; a main-CPU reset at `$033264` preceded 39 contiguous positive count writes through `$0027` before target entry, contributed by main CPU (19) and Sub-Y (20). No Sub-X count write appeared in this prefix. The private frozen JSON at `build/private/phase1b-projection-count124-frozen.json` has SHA-256 `4f6be93226fe61483b08dbd0e9d0f731a12d18d72c04ec42615dbe0405c4514e` and predicts **`$0027`** at target entry. The parser uses only the debug-log prefix before `PROJECTION_COUNT_TARGET`; the debugger's `quit` may allow a final other-CPU event after that marker, which is deliberately excluded. The input debug/control SHA-256 values are `472663c0f19ad9114e56802dcfe1373cb032566accafbfc5003536b90af2f070` and `1469dec98ee6bb3edc3dd3dd83889ecabdff52cd1c0c18a1248877fca13bd07b`. No pulse-124 output was opened at this checkpoint.

**Limits:** this predicts from earlier *observed writer events*, not from steering or track state alone. It does not explain why each earlier object was emitted, where the Sub-Y records originate, or how many Sub-Y writes can interleave after target entry. A successful entry-count match would narrow the next test to the target-entry-to-lock interval.
