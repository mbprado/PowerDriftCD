# Phase 1B: Sub-Y checkpoints around the shared-list lock

**Question and hypothesis:** after the [failed held-out pulse-104 slot prediction](2026-10-30-late-interleaving-contrast-result.md), can a code checkpoint between Sub-Y's entry state and list count write distinguish schedules where Sub-Y reaches the shared lock before the main CPU? The existing baseline is pulse 72 copying `$0260`, pulse 116 copying `$0250`, and pulse 104 copying `$0230` at marker 981. A useful result would identify the exact order and a pre-lock observation suitable for a new frozen prediction. A checkpoint that merely records which CPU already won is diagnostic, not predictive.

**Method — verified by execution:** a small optional `PDRIFT_PROJECTION_LOCK_CHECKPOINTS=1` extension to `projection_lock_interval` sets breakpoints on Sub-Y at `$012A4E` (guard), `$012A76` (middle), `$012ABA` (branch), `$012B3A` (lock attempt), and `$012B60` (count increment). Existing main-CPU entry, lock-attempt, locked, copy and release breakpoints remain active. The events share MAME's ordered debugger log. Each checkpoint reports the shared count and lock byte. Its label gives the Sub-Y breakpoint address; the debugger action's `pc`/`a0` were deliberately omitted because prior watch actions displayed the debugger-visible main CPU registers. The separate CPU-local count tap verifies actual Sub-Y `$012B60` writes. No ROM or emulator source was changed.

Run from a fresh ignored `build/private/phase1b-checkpoint-final-pulse72` directory, replacing `72` and its directory with `116` or `104` for the other schedules:

```sh
env SDL_VIDEODRIVER=dummy PDRIFT_SNAPSHOT_DIR=. PDRIFT_DEBUG_WATCH=projection_lock_interval PDRIFT_PROJECTION_LOCK_START=980 PDRIFT_PROJECTION_LOCK_END=982 PDRIFT_PROJECTION_LOCK_SUBY_PC=1 PDRIFT_PROJECTION_LOCK_CHECKPOINTS=1 PDRIFT_SEQUENCE_END_FRAME=982 PDRIFT_STEER_PULSE=72 PDRIFT_STATE_LOAD=/Users/murilo/repos/PowerDriftCD/build/private/phase1b-range-state-seed/callback950.sta /private/tmp/pd-mame0289-render989/mame pdrift -rompath /Users/murilo/repos/PowerDriftCD/build/private/phase1b-roms -noreadconfig -video none -sound none -nothrottle -seconds_to_run 18 -debug -debugger none -debuglog -autoboot_script /Users/murilo/repos/PowerDriftCD/tools/phase1b_mame_input.lua > phase1b-input.log 2>&1
```

**Results — verified by execution:** all three MAME runs exited successfully. At the `$0C1D00` main-object entry in marker 981, count and lock were `$0025/clear` for pulses 72 and 116, and `$0023/clear` for pulse 104.

| Pulse | Ordered events from main entry through copy | Copy count / slot |
|---:|---|---|
| 72 | Sub-Y guard → middle → branch → lock attempt → count write `$0026` → main lock/copy | `$0026 / $0260` |
| 116 | Main lock/copy; Sub-Y's next guard and count write occur after release | `$0025 / $0250` |
| 104 | Main lock/copy; Sub-Y's middle, branch, lock attempt and count write `$0025` occur after release | `$0023 / $0230` |

For pulse 104, a Sub-Y guard checkpoint with shared count `$0022` occurred before main entry, yet main acquired the lock first at count `$0023`. The input-only capture also placed Sub-Y at `$012A76` at main entry. Thus greater apparent Sub-Y code-path progress at entry was **not** a reliable winner indicator. In contrast, pulse 72 reached its guard only after main entry but completed its count write before main's lock attempt. These are observed event orders; they are not emulated-cycle durations or a general scheduling algorithm. Instrumented copy outcomes agree with the earlier, less instrumented traces, but a small instrumentation effect on unobserved timing cannot be ruled out.

**Assessment — verified by execution for order, unsupported for prediction:** the checkpoint trace pinpoints the immediate dependency: whether Sub-Y completes `$012B3A–$012B60` before main reaches `$033E68`. Observing that completion in the same interval explains the slot, but it reads the outcome-producing work and supplies no earlier-state predictive rule. The proposed checkpoint-based held-out prediction therefore was **not run**. Retrofitting a rule from these three schedules would repeat the failed PC-signature mistake.

**Next targeted experiment — hypothesis:** trace the long Sub-Y path from `$012A76` to `$012B3A`, especially arithmetic-device accesses and branch outcomes, alongside main progress from `$033D1E` to `$033E68`. Seek a measurable pre-entry dependency that predicts relative progress. If none is found within a bounded probe, treat cross-CPU slot selection as a timed runtime outcome and use an explicit synchronization boundary in any future reference replay rather than guessing from the entry PC.
