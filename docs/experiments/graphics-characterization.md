# Phase 1 graphics hardware characterization

## Experiment 1: ASIC transformation validation (2026-10-19)

**Hypothesis:** a sub-CPU program can use a generated 4-bit stamp, a 2M Word RAM stamp map, and per-line trace vectors to make the Sega CD graphics ASIC write correct VDP-shaped output. **Baseline:** Phase 0 established owner-authorized private U.S. disc boot, sub-CPU level-2 callbacks, and 2M Word RAM transfer in BlastEm. **Method:** generate a 16×16 color-grid stamp and four independent expected 128-byte images; run identity, 2× enlargement, 90° rotation, and combined enlargement/rotation in sequence; transfer Word RAM to the main CPU; compare every one of the 64 output words per case. **Expected evidence:** GRON clears, all 256 comparisons pass, and the debugger reaches `G0OK` rather than `G0ER` or `G0TO`.

**Verified by execution:** the corrected image passed all four cases in BlastEm 1.0.0 under the owner-supplied U.S. Model 2 BIOS. Main CPU D3 was `$47304F4B` (`G0OK`), status words at `$FF1100..$FF1106` were `$4700,$4701,$4702,$4703`, and the first two words of the final image at main-visible `$210000` were `$DDDD,$DDDD`. The test compares each output word with a generated expected image; merely writing ASIC registers would not pass. An initial run passed the first three cases and failed the combined case at word 2 (`$DDD9` versus `$DDDD`); the trace started at source Y=15.0 rather than 15.5, exposing the fractional-coordinate sampling behavior. Correcting the trace to 15.5 made the fourth case pass. This is a BlastEm result; no physical hardware has been tested.

**Documented only:** Sega's [Mega-CD Software Development Manual](https://segaretro.org/images/archive/6/6f/20190509144929%21Mega-CD_Software_Development_Manual.pdf), section 12, describes 16×16 and 32×32 stamp maps, 4-bit source pixels, output in image-buffer cell layout, and per-line start X/Y and delta X/Y trace vectors. The tested sub-CPU registers are `$FF8058` (stamp mode and busy), `$FF805A` (map base), `$FF805C` (output vertical cell size), `$FF805E` (output base), `$FF8060` (output offset), `$FF8062/$FF8064` (width/height), and `$FF8066` (trace base and start). The [hardware manual](https://segaretro.org/images/5/51/Mega-CD_Hardware_Manual.pdf) lists the same graphics register block. The test uses an in-bounds 256×256 map and 2M Word RAM owned by the sub-CPU throughout conversion. BlastEm's public `cd_graphics.c` and `cd_graphics.h` were consulted to resolve scan/OCR ambiguities; the installed binary was not altered. The official manual and emulator source disagree on out-of-bounds repeat polarity; this test does not rely on that behavior.

**Verified by execution:** the original source stamp occupies sub-visible `$080080..$0800FF` (128 bytes), with stamp-map entries at `$0A0000`, trace vectors at `$0B0000` (four 16-bit values per output line), and ASIC output at `$090000`. Each map entry selects stamp 1, avoiding the documented stamp-zero restriction. The trace uses a `$0800` delta for one source pixel per destination pixel, `$0400` for a half-pixel step, and an eighth-pixel X/Y start unit in the tested BlastEm path. The combined case's half-pixel correction is direct evidence of fractional sampling in this configuration. The tested source, map, trace, and output ranges do not overlap. The test did not exercise 32×32 stamp mode, stamp-entry flip/quarter-turn flags, priority modes, boundary repeat, or 1M/1M Word RAM.

## Experiment 2: ASIC performance

**Hypothesis:** the ASIC start-to-busy-clear interval increases with output pixel count and can be separated from setup and ownership work in the emulator. **Method:** the sub-CPU prepares the same generated stamp and a trace table for each of 16×16, 32×32, and 64×64 outputs. At each size it performs scaling, 90° rotation, and combined scaling/rotation. It reads the shared 12-bit stopwatch before writing `$FF8066` and after `$FF8058` reports GRON clear; a back-to-back timer-read control is recorded. The main CPU separately times the ownership request, callback, stamp/map/output preparation, ASIC operation, and return through a composite interval. It independently checks the sum of every output word against a generated expectation. The nine cases run in forward, reverse, then forward order.

**Verified by execution:** all 27 cases completed with correct output sums and the `GBOK` debugger marker in BlastEm 1.0.0 with the owner-supplied U.S. Model 2 BIOS. The three observations per case below are emulated stopwatch ticks, not host time or physical-console measurements. The stopwatch control was zero ticks in all 27 cases, showing that its 30.72 µs nominal resolution is too coarse to price two adjacent reads.

| Output | Transform | ASIC start to busy clear, 3 runs | Composite request/setup/ASIC/return, 3 runs | Output bytes |
| --- | --- | --- | --- | ---: |
| 16×16 | Scale | 6, 7, 7 | 36, 36, 36 | 128 |
| 16×16 | Rotate | 7, 7, 7 | 35, 49, 36 | 128 |
| 16×16 | Combined | 7, 6, 7 | 35, 36, 35 | 128 |
| 32×32 | Scale | 30, 24, 25 | 73, 69, 68 | 512 |
| 32×32 | Rotate | 24, 24, 25 | 69, 69, 68 | 512 |
| 32×32 | Combined | 25, 25, 25 | 69, 68, 76 | 512 |
| 64×64 | Scale | 97, 97, 97 | 193, 192, 193 | 2,048 |
| 64×64 | Rotate | 97, 97, 97 | 193, 193, 195 | 2,048 |
| 64×64 | Combined | 97, 97, 97 | 193, 206, 205 | 2,048 |

**Measurement interpretation:** the sub interval includes the trigger write, polling loop, and final timer read, so it is an ASIC completion *observation*, not an isolated internal processing time. The main composite includes ownership, interrupt/callback latency, preparation of the stamp/map/trace/output, ASIC work, and return, but excludes main output checksum verification. For 64×64, 97 ticks correspond to about 2.98 ms using Sega's nominal 30.72 µs/tick; this is a conversion of emulated ticks, not a measured stock-hardware duration. Every adjacent timer pair is well below the 4096-tick wrap; the modular subtraction would alias if a full lap occurred unnoticed, but the observed callback paths and 64×64 scale make that implausible here. A 16×16 rotate composite outlier of 49 ticks and a 32×32 scale first-run 30-tick ASIC interval show sensitivity to execution order or contention; do not choose an architecture from a single sample.

**Verified by execution:** the earlier [paired Word RAM phases](2026-10-19-us-wordram-paired-phases.md) supply a separate ownership/interrupt baseline, but their path differences are also composite and are not subtracted from these graphics windows as if they were pure ownership latency. This experiment's 2M RAM transfer is always serialized around sub-CPU conversion; a 1M/1M overlap result is still **unsupported**.

## Experiment 3: Genesis VDP transfer and display

**Hypothesis:** the ASIC's VDP-cell-layout output can be displayed without a format conversion, and a small repeated region can fit within NTSC VBlank. **Method:** the sub-CPU transforms the original stamp to a 32×32, 512-byte output, checks its busy state, and returns 2M Word RAM. The main CPU checks all output words against the expected sum, then places 16 tiles in VRAM at `$0020` and a 4×4 tile map on plane A. On alternating frames it writes directly from main-visible Word RAM through the VDP data port, or copies 512 bytes to main RAM `$FF6000` and requests VDP memory-to-VRAM DMA from that staging address. A new ASIC transform is prepared between VBlanks. The main CPU records 120 VBlank edges and whether VBlank remains asserted at upload completion.

**Verified by execution:** BlastEm displayed the full 32×32 color image after a corrected plane-map address was used. The [captured original-asset frame](data/graphics-vdp-model2.png) contains exactly 1,024 nonblack pixels within X=112–143 and Y=105–136 of BlastEm's 256×240 PNG. The main CPU reached `GVOK` with 120 completed frames and no output-checksum error. The initial version reached `GVOK` but showed a black screen because the tile-map row address was doubled; this demonstrates why successful VRAM writes and checksums alone were insufficient evidence of display. The corrected run's private ISO SHA-256 was `251117a070e586f56a3b641384b9da7c72e3806f38dce75d70cff623fbb0c087`; screenshot SHA-256 `9698b39a0be5f0db133d6627f74a6e17f2f032a27520fdc686f507c88d5a8566`.

| 32×32 path, 512 output bytes | Samples | CPU staging ticks, min/median/max | VRAM upload ticks, min/median/max | VBlank upload overruns |
| --- | ---: | ---: | ---: | ---: |
| CPU writes directly from Word RAM | 60 | 0/0/0 | 24/24/25 | 0 |
| DMA from a checked main-RAM copy | 60 | 24/25/25 | 7/7/8 | 0 |

**Verified by execution:** successive VBlank starts were 543–544 stopwatch ticks apart in all 119 comparable intervals; the first interval has no prior frame start and is excluded. The DMA upload itself was shorter than CPU writes, but its staging copy made its measured 512-byte transfer path longer in total (typically 32 ticks versus 24 ticks) in this code. The DMA stage and upload measurements are adjacent but separate, with 12-bit modular subtraction. Upload timing includes VDP control-register setup and CPU polling; it is not pure VDP bus time. The screenshot proves the final (DMA) frame was visible; alternating CPU frames were logged but were not independently captured in this run. The raw 120-frame records and parser are [here](data/graphics-vdp-model2.json) and in `tools/parse_graphics_vdp.py`; full ignored BlastEm log SHA-256 `dbaca0b159f35e2da3ce2269971dd4096cb293faf0d493bb9a9d9a779ee42797`.

**Documented only:** Sega's [Genesis Software Manual](https://segaretro.org/images/9/95/GenesisSoftwareManual.pdf), VDP DMA section, specifies memory-to-VRAM transfer length in words, source registers, DMA busy status, and substantially higher VBlank access capacity than active scan. Sega's [Mega-CD Hardware Manual](https://segaretro.org/images/5/51/Mega-CD_Hardware_Manual.pdf) says 2M Word RAM must be assigned to the main side for VDP DMA and documents a one-cycle delayed read from Word RAM by VDP DMA. Therefore this experiment stages DMA from main RAM; it does not claim direct Word RAM DMA is safe or fastest on physical hardware. The 32×32 output was already in tile format; its CPU conversion cost was zero. The staging copy is the measured arrangement cost for the DMA path.

**Reproduction — verified by execution:** `sh scripts/build-graphics-vdp.sh build/private/us-m1-startup-prefix.bin`, then `script -q build/evidence-graphics-vdp-pass1.log /private/tmp/pd-blastem-us-m2-5s/blastem -r U -d /Users/murilo/repos/PowerDriftCD/build/private/graphics-vdp-us.cue`. ### 64×64 transfer and scheduling checkpoint

**Hypothesis:** 2,048-byte uploads may cross the VBlank deadline if the main CPU performs staging inside VBlank, even when the ASIC itself finishes well before the next frame. **Method:** the same checked source stamp and three transforms generated a 64×64 image (64 VDP tiles). The original alternating CPU/direct and staged-DMA transfer loop was tested first. A second build moved the DMA staging copy to the preceding active period. A third used only that pre-staged DMA path for all 120 updates. All three builds use the same U.S. Model 2 BIOS and BlastEm 1.0.0, check every output word's sum before upload, and read the VDP VBlank bit after upload. The [64×64 screenshot](data/graphics-vdp-64-model2.png) shows all 4,096 pixels on plane A; its SHA-256 is `26f3f13dc1614581eea47c3097484aae02584bbaabcea1b82da336c7478089a7`. The DMA-only final screenshot was byte-identical.

| 64×64 schedule and path | Samples | Staging ticks, median | Upload ticks, median | Uploads outside VBlank | One-frame / two-frame start intervals |
| --- | ---: | ---: | ---: | ---: | ---: |
| Stage in VBlank, alternating CPU direct | 60 CPU | 0 | 133 | 60 | Combined run: 60 / 59 |
| Stage in VBlank, alternating DMA | 60 DMA | 97 | 265 | 60 | Combined run: 60 / 59 |
| Pre-stage, alternating CPU direct | 60 CPU | 0 | 133 | 60 | Combined run: 59 / 60 |
| Pre-stage, alternating DMA | 60 DMA | 97 | 26 | 0 | Combined run: 59 / 60 |
| Pre-stage, DMA only | 120 DMA | 97 | 26 | 0 | 119 / 0 |

**Verified by execution:** the first alternating run completed all 120 correct transforms and displayed the 64×64 image, but all 120 uploads ended after VBlank. Its frame starts had 59 two-frame gaps. Moving staging before VBlank reduced the DMA upload interval from 264–265 to 26–27 ticks and made all 60 DMA uploads meet VBlank; the 60 CPU uploads still missed, and the alternating run retained 60 two-frame gaps. The DMA-only pre-staged build completed all 120 updates with 119 consecutive one-frame intervals of 543–544 ticks and no VBlank upload misses. In that build, ASIC start-to-busy-clear was 96–107 ticks (median 97), the ownership/prepare/ASIC/return path was typically 193 ticks, staging was 97–98 ticks, and DMA upload was 26–27 ticks. These intervals refer to distinct code windows; adding them gives a rough serial path budget, not an independently measured whole-frame duration. The 64×64 VBlank DMA result is a stronger emulator proof of a functioning end-to-end path than the 32×32 demonstration, but it still does not resemble a full road viewport or prove physical-hardware throughput.

## Experiment 4: continuous pipeline and architecture comparison

**Hypothesis:** continuous, deterministic source-coordinate motion can sustain 60 Hz at a small viewport; precomputing identical frames may eliminate runtime ASIC work but consume enough memory to scale poorly to a road-sized viewport. **Method:** the ASIC build adds one source X pixel per update (wrapping every 16) to every trace line while cycling 2× scale, 90° rotation, and their combination every three updates. The generated checker/grid texture is transformed and checksummed before each upload. The precomputed build stores all 48 unique 32×32 frames (the least common multiple of 16 offsets and three transform states) as 24,576 bytes of original data in its SP module. It copies them once to 2M Word RAM, then displays the exact same ordered frames without runtime ASIC work. Both strategies alternate direct CPU and staged-DMA 512-byte VRAM uploads. Builds targeted 120 updates at 60 Hz and 60 updates at 30 Hz; the latter intentionally skips one VBlank between updates.

| 32×32 strategy and target | Correct updates | VBlank start interval, min–max ticks | ASIC busy median ticks | Runtime ownership/setup/ASIC/return median ticks | VBlank upload misses |
| --- | ---: | ---: | ---: | ---: | ---: |
| ASIC, 60 Hz | 120 | 543–544 | 25 | 72 | 0 |
| ASIC, 60 Hz, transfer order reversed | 120 | 543–544 | 25 | 72 | 0 |
| Precomputed, 60 Hz | 120 | 543–544 | 0 | 0 | 0 |
| ASIC, 30 Hz | 60 | 1086–1087 | 25 | 72 | 0 |
| Precomputed, 30 Hz | 60 | 1086–1087 | 0 | 0 | 0 |

**Verified by execution:** every build reached `GVOK` after its intended frame count; checksum failures would instead stop at `GVER`. The final ASIC and precomputed 60 Hz screenshots were byte-identical, SHA-256 `5b5f74350e3b6cd84bc71aff8fb7dbac14374b29822f28e54b825f2ffbe3bed8`. The [tracked ASIC frame](data/graphics-animation-asic-60.png) shows the moved and transformed 32×32 color grid. The precomputed build's one-time 24 KiB copy/ownership interval was 736 stopwatch ticks (about 22.6 ms at the manual's nominal tick duration); it occurs before the measured display sequence. The ASIC 60 Hz busy interval was 24–35 ticks (median 25); the 35-tick outlier was retained. The full runtime ownership/prepare/ASIC/return interval was 71–85 ticks (median 72). The precomputed approach removes that recurring interval but occupies 24 KiB of Word RAM and requires storing those 48 exact views. This is an exact comparison only for the finite tested motion sequence, not evidence that arbitrary perspective/camera states can be precomputed economically.

**Verified by execution:** reversing the CPU/DMA order kept CPU upload at 24–25 ticks and DMA upload at 7–8 ticks plus a 24–25-tick stage, with no VBlank misses. This order control supports the 512-byte transfer-path result. The original transfer order always paired the three transforms with alternating upload modes, so the reverse build also changes those pairings; neither mode was systematically randomized. All five results are BlastEm emulation, with no physical-hardware validation. They measure emulated VBlank cadence, not host frame presentation speed.

## Preliminary engineering status

**Measured in BlastEm:** the ASIC transformed and displayed original 16×16, 32×32 and 64×64 graphics. At 64×64, the ASIC's observed completion interval was 97 ticks, but an ill-scheduled 2 KiB upload missed VBlank on every attempt. Moving staging outside VBlank and using DMA exclusively restored 120 consecutive 60 Hz updates with correct output. Thus upload *scheduling and ownership/staging* were the resource constraints encountered first in this fixture; the data do not establish the limits of the ASIC for a road-sized image. At 32×32, an exact precomputed animation matched the ASIC image and cadence while removing 72 median ticks of runtime work, at a cost of 24 KiB for 48 views. This comparison strongly favors precomputation for a small, finite view set; it does not generalize to arbitrary camera transforms.

**Preliminary engineering hypothesis:** begin the next prototype with a **64×64 road-texture viewport at 30 Hz**, despite the successful emulated 64×64/60 Hz DMA-only stress result. The lower target leaves room for per-scanline perspective traces, main-CPU road/tile-map work, camera motion, and scenery not present in this test. Treat 128×64 as a measured stress target, then consider 60 Hz only if the complete moving-road pipeline meets its deadlines. The 64×64 target is a prototype size, not a recommended final game resolution.

**Preliminary workload hypothesis:** the sub-CPU should build trace vectors and run ASIC transforms for continuously varying perspective, scale, and banking; the main CPU should schedule VBlank DMA, tile maps, scrolling, palettes, and scene composition. Precompute repeating stamp artwork, coarse transformation components, and fixed scenery states where memory cost is bounded. Start with the verified 2M Word RAM ownership protocol, prepare the next output during active display, and stage 2 KiB to main RAM before VBlank for DMA. Evaluate 1M/1M ping-pong only after a road prototype shows that 2M serialization is a measurable blocker. The documented direct Word RAM DMA delay must be tested with its prescribed workaround before relying on it; it could remove the staging copy, but has not been validated here.

**Major risks and unmeasured quantities:** ASIC sampling quality for a perspective-varying road, trace-table preparation cost, 4-bit palette and tile reuse constraints, VRAM tile capacity, larger VBlank transfers, scenery compositing, double buffering, 1M mode overlap, direct Word RAM DMA behavior, and differences between BlastEm and stock U.S. Sega CD hardware. Physical hardware tests remain unauthorized and were not performed. The official manuals document register behavior and constraints, but no hardware-speed claim is made from this emulator work.

**Next milestone, not implemented:** a dedicated perspective-road prototype with original texture, scanline-varying depth/curvature, elevation and camera banking. It should use the same 64×64/30 Hz starting budget, measure complete frames and VBlank transfers, then expand the viewport only when the end-to-end evidence supports it.

**2026-10-20 follow-up — verified by execution:** the initial [64×64 perspective-road prototype](2026-10-20-perspective-road-prototype.md) completed this next experiment in BlastEm at the 30 Hz starting target. This historical Phase 1 recommendation remains the baseline for the follow-up; arbitrary runtime trace generation and broader road rendering are still open.

**Later 2026-10-20 road characterization — verified by execution:** the [runtime-trace](2026-10-20-runtime-road-traces.md), [phase-indexed](2026-10-20-phase-indexed-road-camera.md), [independent-control](2026-10-20-independent-road-camera-controls.md), and [live-command](2026-10-20-live-road-camera-commands.md) experiments advanced the 64×64 prototype. The sub-CPU now constructs trace rows from shared curve/ridge tables and a five-word camera packet supplied each update; the ASIC transforms the original texture. The 60 test packets are generated offline, so a gameplay camera producer remains **unsupported**. Each live-command Model 2 run completed 60 checked images at 30 Hz; the worst image-ready time was 510 ticks after the prior VBlank, about 33 ticks before the next edge in BlastEm.

**Wider viewport — verified by execution:** the [128×64 live-command experiment](2026-10-20-wide-live-road-pipeline.md) displayed a 4 KiB ASIC output through main-RAM staging and VDP DMA at 30 Hz in three identical 60-update Model 2 runs, with a Model 1 completion checkpoint. A first, otherwise correct build ran at 20 Hz because its wait loop skipped the intended upload VBlank. After correcting that schedule, the worst image-ready time was 859 ticks after the prior VBlank, about 227 ticks before the intended two-VBlank upload edge. The 128×64 ASIC busy window was 192–193 ticks, combined checksum/staging 335–336, and VDP DMA/setup 51–52. These are emulated stopwatch observations; the staging figure is not an isolated copy cost. The displayed screenshot covers all 128×64 pixels. The earlier 64×64 recommendation was a starting prototype target, not a current viewport limit.

**Updated engineering hypothesis:** retain 128×64 at 30 Hz as the next *synthetic* budget while adding one measured scene cost at a time. Runtime ASIC work is useful for continuously varying road geometry; precomputed stamps, curve/ridge samples and finite scenery states can reduce recurring work where storage remains bounded. Continue 2M Word RAM handoff, checksum/stage during active display, and VBlank DMA until a measured bottleneck justifies changing that path. **Unsupported:** 128×64 at 60 Hz, scenery and gameplay costs, full road geometry/occlusion, original-only boot, and performance or compatibility on physical hardware. The 227-tick margin is available only in this fixture and cannot establish an arcade-faithful engine.
