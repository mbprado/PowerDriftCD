**Verified by execution:** the pilot's A0/A1 register values `$FFFFB000/$FFFFA000` are sign-extended short addresses; under MAME's main-CPU mask they select RAM `$1FB000/$1FA000`. These tables are distinct from the ROM-backed geometry samples and coefficient tables already traced elsewhere. Calling the `$0C00A6` output an *angle-like lookup index* has **medium** semantic confidence because it addresses coefficient tables; calling it a camera angle in world units is **unsupported**. The other index `$0C00A4` remains covered by the earlier transform-producer experiment, not the held-out pilot.

**Verified by execution for the tested interval:** one update's `$0C00AE` becomes the next pass's `$0C0098`; projection reads that new offset while still using the prior `$0C00A6/$0C00A4` and translation fields. Only after the projection entry does the main CPU produce the next indices and base translations. This explains why pairing all fields from one end-of-callback snapshot is temporally wrong. The pilot's prediction and target both use markers 961, 963, …, 999 and compare at the post-write `$0346F0` point. No screen-frame or physical hardware timing is inferred from those markers.

**Hypothesis for Sega CD integration:** `$0C00A6` and changing position/offset sources may eventually help select curve, ridge, signed bank, horizon and texture-offset controls, or the art/lookup tables that drive them. A direct one-to-one mapping is **unsupported**. The current 128×64/30 Hz synthetic five-word BlastEm pipeline remains the verified Sega CD baseline. No numerical or visual requirement here forces an interface change; the next useful handoff is a forward sequence from earlier arcade state that can be compared with the current renderer under fixed calibration.
