**Follow-up status — verified by execution:** the bounded pilot below has since been extended with main-CPU steering, `$8A/$86/$88/$7A/$7C` producer tests and a held-out one-update `$7C → $7A` carry. ## Question and decision

**Hypothesis:** a correctly mapped main-CPU program and bounded static instruction analysis can reveal an earlier dependency of the known projection producer, allowing a prediction on an unused MAME input schedule. **Baseline:** `3a6fa81` on `experiment/perspective-road`; owner-private `pdrift` ROM set and callback-950 saved state; prior [transform-producer evidence](2026-10-21-arcade-transform-producer.md). **Acceptance:** verify four ROM chips and seven addresses against live MAME, freeze a producer rule before reading held-out outputs, then predict one upstream field exactly at its callback. The frozen [pilot plan](phase1b-code-led-pilot-plan.md) records a failed ROM-table assumption and its revised RAM-table test before the target replay.

**Result — partial PASS, verified by execution:** program mapping and a narrow predictive producer model succeeded; the held-out pulse-48 run matched **20/20** `$0C00A6` writes at markers 961–999. Ghidra and REA were **NOT RUN**. Consequently this is evidence that instruction-led analysis can produce a predictive *subroutine* model, not evidence that Ghidra/REA improve throughput or that the arcade camera can be predicted from steering and track state alone.

**Documented only by the pinned [MAME Y-Board driver](https://github.com/mamedev/mame/blob/mame0289/src/mame/sega/segaybd.cpp):** the `pdrift` main CPU has a `$000000–$07FFFF` ROM region loaded as four alternating even/odd 128 KiB chips. Separate `subx` and `suby` 68000 program regions each map `$000000–$03FFFF`; the CPUs share `$0C0000–$0CFFFF` RAM. The main CPU maps multiplier registers at `$080000` and divider registers at `$084000`. The `$1F0000–$1FFFFF` main-CPU RAM region includes the two lookup tables used in this pilot. Each CPU needs its own Ghidra program/address space; a raw chip alone is not an executable CPU image.

**Verified by execution:** [the interleaver](../../tools/phase1b_main_rom_map.py) checked all four owner-local chip SHA-1 digests against MAME's `pdrift` definitions and privately assembled a 524,288-byte main-CPU image, SHA-256 `03143b6e3ba0045109e1745d06e04bda0db638f1cd7fadb1eab0b403fae40618`. [The read-only MAME probe](../../tools/phase1b_mame_rom_check.lua) read 16 live bytes at each of `$000000`, `$033B02`, `$033D1E`, `$034680`, `$03483C`, `$034AD8`, and `$034C30`; **7/7 windows matched** the assembled image at the same address. The known `$034680` bytes and the live MAME debugger's 68000 disassembly agree on the word instruction sequence used below. This validates interleaving, byte order and address placement at those points. Ghidra language selection, automatic function boundaries, vectors and cross-references remain **NOT RUN**; the reset-vector bytes were captured but startup control flow was not traced in this pilot.

## One bounded predictive result

**Verified by execution:** the existing static/disassembly evidence at `$034680–$0346EC` initially looked like a ROM table lookup. The first input-only replay showed `A0=$FFFFB000`, `A1=$FFFFA000`, which resolve under MAME's 21-bit main-CPU address mask to **RAM** `$1FB000/$1FA000`. That rejected the original ROM-pointer condition. The revised test captured both 4 KiB tables at callback 960 and 1000; they were byte-identical. With pulse 48 held from callback 960, the main CPU entered the routine 20 times, at odd markers 961–999, with stable pointers. The [independent Python model](../../tools/phase1b_angle_entry_predict.py) consumed only pre-entry state and the earlier table snapshots. It reproduced the depth-indexed lookup, 16-bit arithmetic/shift, optional branch terms and ten-bit mask. Its prediction JSON was written and SHA-256 frozen as `9da3c24c493d424c9a82d784bec2358defdc923edff9e02538abdaf0584cd1da` **before** running the separate target-output replay. That replay observed 20 writes at `$0346F0`; 20/20 values and marker positions matched. Predicted index values ranged `$025–$032`, while the signed state adjustment varied from `$0000` to `$001B`. The private validation JSON SHA-256 is `a8e0c67b8c672870b3c8053d14795816cc12991943d3f042788cbb65fa60fdbb`.

**Important limit:** pulse 48 exercised a changing adjustment but not the optional `$2A` correction, smoothing change, or both-flag `$0200` branch. Those paths are modeled from instructions but not independently validated here. Entry-state `depth` and signed adjustment were *observed before this routine*, not predicted from earlier steering/game state. The model therefore predicts a meaningful upstream transform **from its pre-existing inputs**, but it does not solve the full predictive arcade-to-Sega CD camera problem. The source and update rule for the RAM lookup tables remain **unsupported**.
